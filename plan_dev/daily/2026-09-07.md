## D1 — Tags operativos de Ansible

### Estado

`pending` — prioridad alta; promovido desde `DEPLOY-001` por decisión del
2026-09-07. Ejecutar después de cerrar M4 y antes de M5.

### Objetivo

Incorporar una interfaz de tags familiar para operadores de Elecciones sin
copiar su granularidad histórica ni permitir recorridos inseguros que salteen
dependencias del provisioning.

### Trabajo y archivos

- Revisar nuevamente `/opt/eleccion/msa/deploy/provisioning` como referencia de
  experiencia operativa, sin copiar acoplamientos específicos de aquel sistema.
- Agregar tags de capacidades sobre los `import_playbook` de `site.yml`:
  `validate`, `common`, `database`, `runtime`, `application`, `scheduler`,
  `tls`, `backup`, `security` y `monitoring`.
- Incorporar `redeploy` como recorrido agregado de validación, aplicación,
  scheduler y monitoreo. No debe instalar/reconfigurar base, runtime, TLS,
  backups, hardening ni firewall.
- Evaluar `deploy` como alias documentado del recorrido completo. Si no agrega
  semántica frente a ejecutar `site.yml`, registrar la decisión y omitirlo.
- Mantener las precondiciones críticas con `always` cuando deban ejecutarse aun
  bajo selecciones parciales.
- No agregar inicialmente tags peligrosamente granulares como `migrate`,
  `restart`, `reset_db`, `borrar` o equivalentes.
- Mantener rollback, restore y bootstrap de acceso como playbooks operativos
  separados.
- Actualizar `bin/check-deploy` para detectar regresiones en el contrato de tags.

### Validación automática obligatoria

- Ejecutar `bin/check-deploy` con todas las versiones soportadas de
  `ansible-core` por `requirements-control.txt`.
- Validar `site.yml --list-tags` y `site.yml --list-tasks`.
- Ejecutar `--tags redeploy --check --diff` y verificar que no incluya database,
  runtime, TLS, backup, security ni firewall.
- Probar ejecución selectiva de cada tag de alto nivel y una segunda ejecución
  idempotente en Vagrant antes de usar los tags sobre testing.
- Ejecutar `git diff --check`.

### Validación manual sugerida

- Desde PC Uni revisar que el recorrido principal sea reconocible y ejecutar en
  testing `ansible-playbook -i inventories/testing/hosts.yml site.yml --tags redeploy --check --diff`.
- Comparar la lista efectiva de tareas con el alcance documentado antes del
  primer apply selectivo.

### Stop

- Detener si la propagación de tags cambia entre versiones soportadas de
  Ansible, si `redeploy` incluye infraestructura fuera de alcance o si una
  ejecución parcial puede omitir una validación necesaria.
