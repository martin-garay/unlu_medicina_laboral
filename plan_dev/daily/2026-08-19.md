# Daily 2026-08-19 — Deploy testing single-host

## Objetivo del día

Preparar el camino de despliegue a testing sobre un servidor dedicado Debian 13,
validando primero la topología Vagrant `single` y dejando el inventory real listo
para operar con usuario `deploy`.

## Decisiones vigentes

- El servidor de testing es Debian 13 `trixie`.
- Testing usará un único servidor en `app_servers` y `db_servers`.
- El usuario operativo será `deploy`; `root` sólo podrá usarse como acceso inicial
  de bootstrap y no debe quedar en el inventory normal.
- No se usa `ProxyCommand` para testing dedicado.
- Mientras no existan certificados institucionales, testing usará
  `tls_provider: local_ca` sólo para validar convergencia técnica.
- El tag previsto para testing es `testing-2026-08-19-01`, pero se recreará recién
  después de validar Vagrant.

## M2 — Diagnosticar y estabilizar Vagrant single

### Estado

`blocked`

### Objetivo

Levantar o recuperar `medicina-single`, guardar snapshot de Debian limpio y dejar
lista la VM para convergencia completa.

### Validación automática obligatoria

- `MEDICINA_VAGRANT_TOPOLOGY=single bin/vagrant status`
- `MEDICINA_VAGRANT_TOPOLOGY=single bin/vagrant ssh medicina-single`
- `ansible all -i inventories/vagrant/single/hosts.yml -m ping`

### Validación manual sugerida

- Confirmar desde VirtualBox que la VM bootea si vuelve a aparecer timeout SSH.

### Stop

- No destruir la VM antes de inspeccionar estado y acceso SSH.
- Detener si la VM no llega a login ni SSH después del diagnóstico.

### Diagnóstico

- `bin/vagrant status` y `bin/vagrant ssh-config medicina-single` fallan antes
  de inspeccionar la VM porque el provider VirtualBox no queda usable para
  Vagrant 2.4.9.
- `VBoxManage --version` informa `7.2.14r174565`.
- `VBoxManage` advierte que no existe `/dev/vboxdrv` y sugiere ejecutar
  `/sbin/vboxconfig`.
- `vagrant` del sistema no está instalado en `PATH`; se usa
  `deploy/.tools/vagrant-2.4.9/vagrant`.
- `VAGRANT_DISABLE_STRICT_DEPENDENCY_ENFORCEMENT=1` no cambia el resultado.

### Acción necesaria fuera del repo

Un operador con privilegios administrativos debe reparar el provider VirtualBox:

```bash
sudo /sbin/vboxconfig
```

Si eso no restaura `/dev/vboxdrv`, reinstalar o reparar el paquete VirtualBox
7.2.14 y volver a verificar:

```bash
VBoxManage --version
ls -l /dev/vboxdrv
```

Luego reanudar M2 desde el inicio.
