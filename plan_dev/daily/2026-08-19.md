## M2 — Diagnosticar y estabilizar Vagrant single

### Estado

`blocked`

### Objetivo

Levantar o recuperar `medicina-single`, guardar snapshot de Debian limpio y dejar
lista la VM para convergencia completa.

### Validación automática obligatoria

- `MEDICINA_VAGRANT_TOPOLOGY=single bin/vagrant status`
- `MEDICINA_VAGRANT_TOPOLOGY=single bin/vagrant ssh medicina-single`
- `ansible all -i inventories/vagrant/single/hosts.yml -m ping`

### Validación manual sugerida

- Confirmar desde VirtualBox que la VM bootea si vuelve a aparecer timeout SSH.

### Stop

- No destruir la VM antes de inspeccionar estado y acceso SSH.
- Detener si la VM no llega a login ni SSH después del diagnóstico.

### Diagnóstico

- `bin/vagrant status` y `bin/vagrant ssh-config medicina-single` fallan antes
  de inspeccionar la VM porque el provider VirtualBox no queda usable para
  Vagrant 2.4.9.
- `VBoxManage --version` informa `7.2.14r174565`.
- desde la sesión del agente, `VBoxManage` advierte que no existe `/dev/vboxdrv`
  y sugiere ejecutar `/sbin/vboxconfig`.
- en la terminal del operador, `/dev/vboxdrv` sí existe después de ejecutar
  `/sbin/vboxconfig`, por lo que el bloqueo restante parece estar en la vista
  aislada de `/dev` del sandbox de Codex, no necesariamente en el host.
- `vagrant` del sistema no está instalado en `PATH`; se usa
  `deploy/.tools/vagrant-2.4.9/vagrant`.
- `VAGRANT_DISABLE_STRICT_DEPENDENCY_ENFORCEMENT=1` no cambia el resultado.
- dentro del sandbox, `lsmod` muestra `vboxdrv` y `vboxnetflt`, pero `/dev/vboxdrv`
  y `/dev/vboxnetctl` no están disponibles.
- en la terminal del operador, `bin/vagrant status` informa
  `medicina-single poweroff (virtualbox)`.
- `bin/vagrant ssh-config medicina-single` informa que el provider no está listo
  para SSH porque la VM está apagada.
- `ansible ping` a `192.168.56.10` falla por timeout, consistente con la VM
  apagada.
- en la terminal del operador existe `/dev/vboxdrv`, pero falta
  `/dev/vboxnetctl`; esto puede bloquear la red host-only al ejecutar
  `vagrant up`.
- `MEDICINA_VAGRANT_TOPOLOGY=single bin/vagrant up` confirma el bloqueo:
  `VBoxManage hostonlyif create` falla porque `VBoxNetAdpCtl` no puede abrir
  `/dev/vboxnetctl`.
- luego de reparar la red host-only, `vagrant up` avanza y la VM permite login
  manual, pero Vagrant expira esperando SSH dentro del `boot_timeout`.
- como la VM llega a login, se aumenta `config.vm.boot_timeout` a 1200 segundos
  para tolerar el primer arranque lento antes de considerar fallida la VM.

### Acción necesaria fuera del repo

Si `/dev/vboxdrv` no existe en la terminal del operador, reparar el provider:

```bash
sudo /sbin/vboxconfig
```

Si `/dev/vboxdrv` existe fuera del sandbox, ejecutar la validación de M2 desde la
terminal del operador, fuera de Codex:

```bash
VBoxManage --version
ls -l /dev/vboxdrv /dev/vboxnetctl
cd /home/mgaray/UNLu/unlu_medicina_laboral/deploy/provisioning
MEDICINA_VAGRANT_TOPOLOGY=single bin/vagrant status
MEDICINA_VAGRANT_TOPOLOGY=single bin/vagrant up
MEDICINA_VAGRANT_TOPOLOGY=single bin/vagrant ssh-config medicina-single
ansible all -i inventories/vagrant/single/hosts.yml -m ping
```

Pegar la salida para reanudar M2 sin destruir la VM.

Si `vagrant up` expira pero el login manual funciona, reintentar sin destruir:

```bash
MEDICINA_VAGRANT_TOPOLOGY=single bin/vagrant status
MEDICINA_VAGRANT_TOPOLOGY=single bin/vagrant ssh medicina-single -c 'hostname; whoami; sudo -n true'
ansible all -i inventories/vagrant/single/hosts.yml -m ping
```

Si `vagrant up` falla por `/dev/vboxnetctl`, revisar módulos y devices de red
host-only de VirtualBox fuera de Codex:

```bash
lsmod | grep '^vbox'
sudo modprobe vboxnetadp
sudo modprobe vboxnetflt
ls -l /dev/vboxdrv /dev/vboxnetctl
VBoxManage list hostonlyifs
```

Si `modprobe vboxnetadp` falla o no crea `/dev/vboxnetctl`, reparar o reinstalar
VirtualBox 7.2.14 y volver a ejecutar `/sbin/vboxconfig`.
