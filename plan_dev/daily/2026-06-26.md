# Daily Plan
## Fecha
2026-06-26

## Nombre
Menus conversacionales y deduplicacion de webhooks

## Objetivo del dia
Mejorar la experiencia de WhatsApp reemplazando respuestas numeradas por menus interactivos donde corresponda y corregir el bug por el cual mensajes duplicados o reintentados pueden avanzar el flujo sin una respuesta nueva del usuario.

## Estado actual resumido

- El menu principal ya usa mensajes interactivos de WhatsApp mediante `ConversationOutboundMessage::menu`.
- Varios pasos internos siguen enviando texto con opciones numeradas construidas en handlers o templates.
- La entrada de WhatsApp ya captura `interactive.button_reply.id`, pero varios validadores de opciones solo leen `text`.
- No existe deduplicacion previa por `provider_message_id`; `conversacion_mensajes.provider_message_id` solo tiene indice, no restriccion unica ni guard de idempotencia.
- El webhook ignora payloads sin `messages.0`, pero no existe test explicito para status callbacks ni para reintentos del mismo `wamid`.
- No existe `plan_dev/daily/2026-06-26.md` previo; este archivo abre el plan del dia.

## Reglas de ejecucion

- Ejecutar milestones en orden, salvo autorizacion explicita indicada en cada milestone.
- No hardcodear textos ni titulos de botones en codigo: usar `lang/es/whatsapp.php` y `config/medicina_laboral.php`.
- No romper compatibilidad con respuestas por texto o numero mientras exista uso real desde WhatsApp.
- Toda opcion convertida a menu debe seguir funcionando con `button_id`, texto legacy y alias numerico cuando corresponda.
- Todo cambio de flujo debe actualizar tests y documentacion/diagramas si cambia el camino conversacional.
- Validar limites de WhatsApp antes de implementar menus: maximo 3 botones por mensaje interactivo y titulos de boton cortos. Si un titulo excede el limite practico, frenar y pedir definicion de texto corto.

## M3
### ID
M3

### Nombre
Corregir avance fantasma por webhooks duplicados

### Objetivo
Evitar que un mismo mensaje entrante de WhatsApp, reintentado o duplicado por el proveedor, se procese mas de una vez y avance el flujo sobre un paso posterior.

### Hipotesis de bug
El caso reportado es consistente con reintentos del mismo mensaje `wamid`: un mensaje viejo vuelve a entrar cuando la conversacion ya cambio de paso. Como no hay deduplicacion por `provider_message_id`, el texto duplicado puede validarse contra el paso nuevo y disparar respuestas sin que el usuario haya contestado.

### Alcance
- Agregar guard de idempotencia antes de ejecutar el handler del paso.
- Si llega un `provider_message_id` entrante ya registrado, responder `ok` sin transicionar ni enviar nuevos mensajes.
- Registrar evento tecnico opcional de duplicado ignorado sin duplicar `conversacion_mensajes`, o dejarlo solo en logs si se decide minimizar ruido.
- Agregar tests que reproduzcan:
  - mismo `provider_message_id` dos veces no avanza conversacion
  - no se generan mensajes salientes duplicados
  - payload de `statuses` sin `messages.0` no crea conversacion ni mensaje
- Evaluar si hace falta indice unico parcial futuro sobre mensajes entrantes con `provider_message_id` no nulo.

### No incluye
- Cambiar politica de inactividad.
- Cambiar scheduler.
- Cambiar reglas de validacion de fecha o catálogos.

### Archivos candidatos
- `app/Services/Conversation/ConversationInteractionService.php`
- `app/Services/ConversationMessageService.php`
- `app/Http/Controllers/WhatsappWebhookController.php`
- `app/Models/ConversacionMensaje.php`
- `tests/Feature/Services/Conversation/ConversationInteractionServiceTest.php`
- tests HTTP de webhook si existen o se agregan.

### Validacion automatica obligatoria
- `make test`
- `git diff --check`

### Validacion manual sugerida
- Enviar un mensaje por WhatsApp real y verificar que un reintento del mismo webhook desde ngrok no dispare una segunda respuesta.
- Revisar `make logs` buscando `provider_message_id` y estado de conversacion.

### Stop conditions especificas
- Si no hay forma segura de identificar duplicados porque `provider_message_id` viene vacio en algunos tipos de mensaje, aplicar deduplicacion solo cuando exista id y documentar el caso.
- Si se propone constraint de base de datos y choca con datos existentes, dejar migracion para corte separado y cerrar con guard de aplicacion.

### Entregable esperado
- Reintentos del mismo webhook no avanzan el flujo.
- Tests de regresion del bug.

### Si queda bloqueado, ¿se puede avanzar al siguiente milestone?
- `no`

### Estado
`done`

### Resultado de ejecucion
- Se agrego lookup de mensaje entrante por `provider_message_id` en `ConversationMessageService`.
- `ConversationInteractionService` corta el procesamiento antes de resolver handlers cuando detecta un mensaje entrante duplicado.
- El duplicado responde sin mensajes salientes, no transiciona la conversacion, no registra otro `conversacion_mensaje` y deja log operativo `Duplicate inbound message ignored`.
- Se agrego test de regresion que reproduce un mismo `wamid` entrando dos veces luego de avanzar a `identificacion_nombre`.
- Se agrego test HTTP para payload de `statuses` sin `messages.0`, validando que responde `no_message` sin crear conversacion ni mensajes.
- No se agrego constraint unico de base en este corte; queda como mejora futura si se quiere reforzar idempotencia a nivel DB.

### Validacion ejecutada
- `git diff --check`: sin errores.
- `make test`: `211 passed`, `879 assertions`.
