## CAT-001 — Catálogos de opciones conversacionales

Estado: `done`. Fase: `DONE`.

### Goal / objetivo

Administrar desde `/admin` los catálogos de sedes, tipos de ausentismo, tipos de
certificado y parentescos, y usar una misma fuente DB para mostrar/validar
opciones nuevas en sesiones de chat. Mantener `jornada_laboral` como texto libre.

### Scope / fuera de alcance

- Incluye migraciones, modelos/servicios, seed inicial desde opciones versionadas,
  recursos Filament con permisos y auditoría, integración de chat, snapshots,
  pruebas, documentación del esquema y decisiones CAT-001.
- Los códigos son aliases estables del dominio; el ID incremental queda interno.
- Mantener snapshots históricos; nuevas altas aparecen para sesiones nuevas.
- Fuera: CRUD de jornada, estados, mensajes, menús/acciones técnicas, plantillas,
  settings, catálogos de padrón Mapuche, storage M5, deploy y catálogo oficial no
  provisto. Las tres sedes actuales son semilla de compatibilidad, no acreditación
  de lista institucional completa.

### Dependencies / contratos compartidos

- Cada catálogo: `id`, `codigo` único e inmutable, `nombre`, `activo`, `orden`,
  timestamps. Tipos de ausentismo agrega `requiere_datos_familiar`.
- Opciones del chat se derivan de registros activos ordenados por `orden,id`;
  aceptar código, etiqueta, botón y ordinal. Inactivos no se ofrecen ni aceptan.
- Los valores admitidos actualmente se siembran idempotentemente sólo si no
  existen. Claves semánticas existentes se preservan. No agregar FKs a avisos ni
  anticipos ni reescribir JSON histórico.
- Para ausentismo, la capacidad de solicitar datos familiares se configura por
  atributo del registro, no por el texto/orden. No permitir borrar códigos usados;
  gestionar disponibilidad con baja lógica.
- Permiso `catalogos.view` / `catalogos.manage`, conceder gestión sólo al rol
  admin; auditar cambios por el servicio existente.

### Acceptance criteria / entregable

- Admin puede crear/editar/desactivar cada catálogo con permiso y auditoría; código
  no cambia al editar y registros referenciados no se borran.
- El chat muestra y acepta opciones activas de DB para identificador, ausencia,
  certificado y parentesco; no muestra ni acepta inactivas.
- El caso familiar sigue solicitando nombre y parentesco cuando el tipo así lo
  define. Las confirmaciones/registros retienen etiquetas históricas.
- Jornada sigue siendo texto libre; no se crea `jornadas_laborales`.
- Config anterior no mantiene otra fuente de opciones activas.

### Validación automática obligatoria / Regression tests

- Tests nuevos de migración/seed, CRUD/permisos/auditoría, menús y validación activa,
  baja lógica, alias estable y snapshots históricos.
- Suite afectada de identificación, aviso familiar y certificado.
- `make test` (si Docker disponible), y `git diff --check`.

### Validación manual sugerida

- Alta, edición de nombre/orden y desactivación en admin; revisar opciones en chat
  interno y validar que el trámite histórico conserva la etiqueta presentada.
- No bloqueante para este corte.

### Risks / condiciones de stop

- PDF no entrega un padrón oficial completo de sedes; seed inicial refleja únicamente
  las tres opciones ya presentes en código.
- Cambios de orden afectan ordinales nuevos. Cada menú conserva una instantánea por
  conversación; respuestas inválidas retienen la instantánea hasta avanzar el paso.
- WhatsApp limita las listas interactivas a 10 opciones; catálogos mayores se
  presentan como texto numerado.
- Jornada es libre y se limita a 255 caracteres por el tamaño de almacenamiento.
- No saltar M5 ni habilitar almacenamiento de certificados como efecto colateral.
